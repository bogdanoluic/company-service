# Company Service

A Go microservice for managing companies through a REST API.

## Features

* Create, retrieve, partially update, and delete companies
* PostgreSQL persistence with Tern migrations
* JWT authentication for mutation endpoints
* Validation and consistent HTTP error responses
* Optimistic locking for concurrent updates
* Transactional outbox events for company mutations
* Structured logging and graceful shutdown
* Docker Compose setup
* Unit and PostgreSQL integration tests
* Liveness and readiness endpoints

## Technology

* Go
* Chi
* PostgreSQL
* pgx
* Tern
* JWT
* Docker
* Testcontainers

## Company model

| Field                 | Rules                                   |
| --------------------- | --------------------------------------- |
| `id`                  | UUID generated by the service           |
| `name`                | Required, unique, maximum 15 characters |
| `description`         | Optional, maximum 3000 characters       |
| `amount_of_employees` | Required, non-negative integer          |
| `registered`          | Required Boolean                        |
| `type`                | Required company type                   |

Allowed types:

```text
Corporations
NonProfit
Cooperative
Sole Proprietorship
```

## Configuration

Copy the example environment file:

```bash
cp .env.example .env
```

Generate a local JWT secret:

```bash
openssl rand -hex 32
```

Store it as `JWT_SECRET` in `.env`.

The application uses standard PostgreSQL environment variables:

```dotenv
PGHOST=localhost
PGPORT=5432
PGUSER=company_service
PGPASSWORD=company_service_password
PGDATABASE=company_service
PGSSLMODE=disable
PGCONNECT_TIMEOUT=5
```

Do not commit `.env`.

## Running locally

Start PostgreSQL:

```bash
docker compose up -d postgres
```

Apply migrations:

```bash
make migrate-up
```

Start the service:

```bash
make run
```

The API is available at:

```text
http://localhost:8080
```

To run the service in Docker:

```bash
docker compose up --build company-service
```

To stop and remove all local data:

```bash
docker compose down -v
```

## Migrations

```bash

```

Database migrations are executed as an explicit deployment step before starting the application, rather than automatically during application startup.

## Authentication

The mutation endpoints require an HS256 JWT containing valid `sub` and `exp` claims:

```text
POST   /companies
PATCH  /companies/{id}
DELETE /companies/{id}
```

The GET endpoint is public:

```text
GET /companies/{id}
```

The service validates tokens but does not issue production login credentials. A development token generator is included:

```bash
make token
make token subject=reviewer ttl=2h
```

## API usage

Store a token in a shell variable:

```bash
TOKEN=$(make token subject=reviewer)
```

### Create

```bash
curl -i \
  -X POST http://localhost:8080/companies \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "ExampleCo",
    "description": "Example company",
    "amount_of_employees": 25,
    "registered": true,
    "type": "Corporations"
  }'
```

Returns `201 Created` and a `Location` header.

### Get

```bash
curl -i \
  http://localhost:8080/companies/$COMPANY_ID
```

### Patch

```bash
curl -i \
  -X PATCH "http://localhost:8080/companies/$COMPANY_ID" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "amount_of_employees": 40,
    "registered": false
  }'
```

PATCH updates only supplied fields. Explicit `false`, `0`, and `null` values are preserved.

### Delete

```bash
curl -i \
  -X DELETE "http://localhost:8080/companies/$COMPANY_ID" \
  -H "Authorization: Bearer $TOKEN"
```

Returns `204 No Content`.

## Error responses

Errors use this format:

```json
{
  "error": "company name already exists",
  "field": "name"
}
```

Common responses:

| Status | Meaning                                       |
| ------ | --------------------------------------------- |
| `400`  | Invalid request or company data               |
| `401`  | Missing or invalid JWT                        |
| `404`  | Company not found                             |
| `409`  | Duplicate name or concurrent update conflict  |
| `500`  | Unexpected internal error                     |
| `503`  | PostgreSQL unavailable during readiness check |

## Health checks

```text
GET /health
GET /health/live
GET /health/ready
```

`/health` and `/health/live` report process liveness.

`/health/ready` verifies PostgreSQL connectivity and returns `503` when the database is unavailable.

## Implementation details

### PATCH semantics

PATCH request fields track whether a value was omitted or explicitly supplied. This allows valid values such as:

```json
{
  "registered": false,
  "amount_of_employees": 0,
  "description": null
}
```

### Optimistic locking

Companies have an internal version number.

Updates succeed only when the stored version still matches the version read by the service. Successful updates increment the version. A stale update returns `409 Conflict` instead of overwriting newer data.

The version is not currently exposed through the HTTP API.

### Transactional outbox

Successful mutations create:

```text
company.created
company.updated
company.deleted
```

The company mutation and outbox insertion run in the same PostgreSQL transaction.

Outbox records are currently stored durably but are not published to an external broker. A Kafka publisher would be a future extension.

Inspect stored events with:

```bash
docker compose exec postgres sh -c \
  "psql -U \"\$POSTGRES_USER\" -d \"\$POSTGRES_DB\" \
  -c \"SELECT event_type, aggregate_id, payload, published_at FROM outbox_events ORDER BY occurred_at;\""
```

## Testing

Run unit tests:

```bash
go test ./...
```

Run static analysis:

```bash

```


## Graceful shutdown

The service handles `SIGINT` and `SIGTERM`, stops accepting new requests, allows active requests to finish within the configured timeout, and closes the PostgreSQL pool.
